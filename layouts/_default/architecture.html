Architecture

One binary. One hash. One source of truth.

Provenance is built around a small set of hard architectural commitments — no privileged built-in types, no server in the critical path, and cryptographic identity for everything that matters. Here's how the pieces fit.

01

The binary is the unit of trust

Provenance distributes as one content-addressed binary. It serves the browser UI locally and runs identically in CI — the same executable, the same hash, in both places. The hash is the validation identity: it's what a customer's CSV evidence is written against.

provenance sha256:9f3a…2c1e
local · browser UI continuous feedback
CI · same binary authoritative gate
02

Schema-as-code, no built-ins

Every entity type — including Requirements — is a schema file in the repo, not a locked-in built-in. New types are added by a normal commit. Records are plain text with frontmatter; typed links between them form the traceability graph.

/entities/requirements/REQ-0142.md
---
type: requirement
status: approved
links:
– risk: RISK‑0087
– verifies: VER‑0304
---
The device shall limit output current to…
03

The hybrid merge gate

The browser gives continuous feedback while you work. The CI-executed binary run is the authoritative gate — it talks to your pipeline through process exit codes only, a thin wrapper around the same rule engine.

git push
→
CI runs binary
→
rule check
→
exit 0 → merge
exit 1 → blocked
04

Three independent hash chains

Binary artifact identity, reproducible builds, and DHF content state are verified separately — so a question about the tool never gets confused with a question about the records it produced.

Binary artifact identity proves the executable being run is the one that was published
Reproducible build proves the published binary was actually built from the published source
DHF content state proves what was actually signed, down to the resolved entity graph
05

Portable by design

Because the record store is a standard git repository and the engine is a single binary, Provenance runs the same way on GitHub, GitLab, Bitbucket, or self-hosted git infrastructure. Moving your DHF is a clone, not a migration.
